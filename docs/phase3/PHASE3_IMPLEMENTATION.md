# Phase 3 | Registration, eligibility, private profiles and account privacy

Release package: 0.5.0-phase3. The source is intended for the existing protected XORA production deployment, not a staging deployment. Installing code and empty schema does not authorize accepting real members. See PRD §§3, 9–12, 18, 20.5, 25–27; API_SPECIFICATION §§2–4, 10–13; DATABASE_SCHEMA §§2–5 and visibility predicate; PHASES §7. Earlier staging-only documents remain historical. This record describes implementation rather than changing the approved product boundary.

## Member journey

1. `/policies` explains who may join, profile visibility, consent, photo restrictions, privacy rights and support. The page explicitly distinguishes a summary from reviewed legal text. `XORA_APPROVED_TERMS_URL` and `XORA_APPROVED_PRIVACY_URL` must be valid HTTPS addresses containing the actual approved, versioned policies before registration is opened.
2. `/account` includes closed-state and controlled signup/sign-in screens. Registration requires an 18+ declaration, current policy versions, matching 12–128 character passwords, and separately chosen marketing consent. The server validates the allowlisted email domain and wraps the Better Auth signup route. The ordinary provider signup path is not exposed. Registration agreement is recorded for a genuine unverified provider user; the member must affirm the policy versions after verifying email and signing in. The acknowledgement is not adult-age assurance. Verification and recovery use the provider's one-time tokens, not homemade reset links.
3. After verified email, the member is associated with a single application account and starts a private draft. Screen name, approximate city, Date/Casual/Both, a short biography, three to five interests, and one to three permitted photos are required for profile submission; partial drafts can be saved. Matching preferences are optional and private. No phone, precise address, exact DOB or raw identity document is collected. Bio contact identifiers and URL patterns are rejected. All visibility options are off initially.
4. Member saves or continues through the wizard. Writes are versioned; replay of identical saved content returns the current saved version. An incompatible concurrent change returns a conflict instead of overwriting it. The browser retains its in-memory draft while a failed request is retried; no member information or session credentials are placed in browser localStorage. A page reload retrieves the last committed server-side draft. The UI warns about unsaved changes. A session can be revoked from the account screen; summaries expose coarse device label and dates, not IP or raw user agent.
5. Photo data is posted as bounded binary to `/api/v1/me/profile/media`. Input accepts JPEG, PNG or WebP only, maximum 3 MiB, valid signatures, matching decoder format, at least 128×128, no animation, at most 16 million pixels. Sharp decodes and re-encodes to WebP, rotates based on orientation, caps dimensions at 1200 px, strips metadata and caps stored output at 1 MiB. The normalized bytes, not the original, go to the production private `xora-profile-media` bucket. SHA-256 verifies reads and makes retries of identical content safe. Wrong content type is rejected. No storage key or reusable signed URL is returned to the browser. Authorized bytes are streamed through server routes with private/no-store caching. A removal first commits a tombstone and unpublishes; then attempts physical purge. Pending purge/orphan reconciliation is an operational obligation; backups follow approved retention.
6. Submit adulthood review separately from content review. Only an approved external/in-person process is permitted. Reviewer records an opaque reference and explicitly attests completion of the process. The portal does not collect identity documents or determine age from a photo. An approval has expiry. Uncertain/underage/rejected outcomes restrict the account/profile and revoke sessions; members may sign in again for privacy/support/appeal access only. Neither declaration, payment, content approval nor an arbitrary client field can approve age. **No actual assurance provider is integrated or approved by this package.** The method and case handoff need approved operational procedure before activation. An external evidence reference is not itself proof.
7. `/admin/reviews` uses the existing session-bound staff TOTP step-up, role permissions and assigned-case checks. Lists contain case IDs, state, timestamp and assignment only. Assigned profile detail exposes submitted display name, biography, broad location, interests and transformed photos; no login contact, DOB, private discovery preferences or payment history. Eligibility reviewer receives method and case status, not raw proof. Case opens/photo reads/decisions create audit events. The reviewer must select an outcome and each current photo decision. The profile version and review version must match. Profile approval alone does not make a member discoverable; an eligible member must explicitly activate after independent eligibility and content approval.
8. Pause is immediate state change; material edits return to draft. Rejected content can be corrected; eligibility restrictions require appeal/support. Profile states: draft, review, changes_requested, approved, active, paused, restricted, rejected. A future discovery predicate checks current account/consent/age-expiry/approved photo state. Phase 3 deliberately contains no discovery results, profile-by-other-account endpoints, matching, introductions, messaging, payment or paid promotion endpoints. Even an active Phase 3 profile is not shown to anyone else.
9. Account settings create idempotent pending export, correction, deletion, appeal or support tickets. Deletion requires a recent verified session, restricts account and profile immediately, revokes sessions, and leaves the ticket for authorized privacy processing. Export/deletion fulfilment, legal holds, review SLAs, support routing and final erasure are not claimed to be automated. Optional communications can be withdrawn separately. User is never promised completed deletion merely because a ticket exists.

## API and contract mapping

| PRD contract | Implementation |
|---|---|
| `/auth/register` | `POST /api/v1/auth/register` checks exact allowed fields, consent, approved email domain, schema activation and production gate |
| Email verification, resend, login, logout, password recovery | Better Auth `/api/auth/verify-email`, `/send-verification-email`, `/sign-in/email`, `/sign-out`, `/request-password-reset`, `/reset-password`; native paths rather than duplicated wrappers |
| `/me`, `/me/profile` | verified owner summary; `GET`, `PUT`/`PATCH` private draft with record version |
| `/me/consents` | `GET` latest version/marketing record; `POST` append current consent record |
| `/me/verification`, `/me/verification/submit` | own case status and submit; never raw evidence |
| `/me/profile/submit`, `/pause`, `/resume` | locked transactions, approval/expiry checks, version validation; `/activate` alias |
| `/me/profile/media` | `GET`, `POST` bounded binary, `DELETE /{id}`, `GET /{id}/view`. Direct server upload intentionally replaces the proposed presigned-intent/complete pair in Phase 3; this avoids accepting unvalidated originals into storage. Ordering/caption and member-to-member media are deferred. |
| `/me/security/sessions` | `GET` coarse own session summaries, `DELETE /{id}` owned revoke |
| `/me/privacy-requests` | GET/POST own status/initiation, `/me/privacy/requests` alias |
| `/admin/reviews/{eligibility,profile}` | GET scoped queue, POST `/{id}/claim`, GET `/{id}`, POST `/{id}/decision`, GET profile `/{id}/media/{photo}`. This consolidated contract replaces proposed `/admin/profile-reviews` endpoints. |
| `/profiles/{accountId}`, `/discovery`, invitations, payments | intentionally unavailable; no public or member-to-member projection exists yet |
| `/api/health/phase3` | monitor-token-protected schema and grant readiness only; no member data |

All mutable member and reviewer requests enforce same-origin checks. Response status codes are stable (`401`, `403`, `404`, `409`, `413`, `415`, `422`, `429`, `503`). The application does not log private payloads or expose database exceptions. Routes require server-resolved identity; IDs supplied by users are never a source of authority. Most writes lock the account and appropriate review/profile version. All application authorization remains server-side; the role is not a substitute for row ownership checks.
