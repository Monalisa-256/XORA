## Release gates

1. Install the separate workflow at the existing path and upload the source ZIP. GitHub must allow Actions to write repository contents for the final import job. The connected integration previously returned 403 on direct workflow writes; the repository owner must install the workflow or grant the necessary repository-scoped permissions. Prefer one reviewed commit containing the workflow and ZIP. The import does not execute uploaded code in the credential-bearing commit job.
2. Confirm the validate job actually runs the Python and Node tests, dependency installation, syntax, build and type check. A skipped or missing test step is not equivalent to passing. The workflow checks the manifest digest again in the write job and uses a non-force push. A concurrent main change aborts the import. Verify the actual source commit after the ZIP disappears; do not assume that a GitHub Actions token push triggers all downstream integrations. Check both provider deployments for the resulting commit and manually redeploy the exact reviewed `main` head if necessary.
3. Render settings: keep the existing build and start commands until a reviewed lockfile is available. Set the HTTP health check path to `/api/health/live` in the existing service dashboard. The connector did not expose this setting. A free-plan service can sleep; a cold start can temporarily return 503 and does not mean the last deploy failed. Do not upgrade the plan without authorization.
4. Check production environment names and host/role/branch against `.env.example`. Verify the actual secret `DATABASE_URL` securely in each provider (do not print or copy it to a public repo). Set TLS mode `require`, `verify-ca` or `verify-full` and prefer the strongest compatible mode. The application rejects weaker or missing modes. Keep `XORA_ENVIRONMENT=production`, test endpoints off and public launch flags unchanged. Do not add production credentials to GitHub CI.
5. Run `npm run verify:production` from an authorized environment with the monitor token and, if needed, an existing Vercel automation bypass credential. Each host must return 200 and the expected JSON status from both endpoints. An unauthenticated 404 from readiness is expected, not a database failure. If readiness fails, inspect provider logs and validate host, branch, role, TLS and runtime credentials; do not switch to the owner role. The script does not print tokens or response payloads. Both hosts must be tested separately.
6. Compare GitHub `main`, the Render live deploy and the Vercel production deployment SHA. Record timestamps and error scan window. If any release gate fails, retain the last healthy deployment and investigate; do not silently skip checks, force push or run migrations automatically. Restore a previous provider deployment only after identifying the exact known-good commit and checking database compatibility.

## Remaining scope

The supplied source lacks a verified dependency lockfile. The local runner has no npm registry access, so installation, full Next.js build, type-checking with application dependencies, dependency audit and real provider readiness must be completed in a network-enabled environment. This archive is not evidence of a new successful remote deployment. Production hosting is separate from public product launch; no authentication, registration, payment or upload feature is enabled by this infrastructure delivery. Older staging-related documents and migration files are preserved as historical records, not instructions to create a new staging environment.
